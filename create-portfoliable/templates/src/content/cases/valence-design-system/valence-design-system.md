# Valence: turning interface decisions into a system

Valence is the Web Component design system behind Portfoliable. It exists to solve a problem that appears in almost every product with a growing interface: once the first components are built, consistency becomes a coordination problem. Colors drift, interaction patterns get copied, accessibility fixes arrive late, and every new screen starts negotiating the same decisions again.

The answer was not a larger component catalog. It was a clearer foundation: native web standards, a small set of design tokens, predictable composition, and a workspace where every component can be explored before it reaches production.

> A design system is not only a collection of components. It is a shared way to make decisions.

[INSERIR IMAGEM 1 — Hero do Valence: um print amplo do Storybook com a navegação lateral, uma área de Canvas e um componente central em destaque. O enquadramento deve fazer o sistema parecer um produto de desenvolvimento, não apenas uma galeria.]

## Built on the platform

Valence uses native custom elements instead of binding the system to a single application framework. A component can be consumed by Portfoliable today and remain available to another JavaScript application tomorrow:

```js
import '@portfoliablejs/valence';

const button = document.createElement('ds-button');
button.setAttribute('label', 'Open case');
button.setAttribute('variant', 'primary');
document.querySelector('#actions').append(button);
```

The components encapsulate their behavior and styling through Shadow DOM. This creates a strong boundary: application styles do not accidentally rewrite a button, and a component can evolve without requiring every consumer to copy its CSS. It also keeps the design system close to the browser’s native composition model—attributes, slots, events, and semantic HTML.

## A structure that scales with the interface

The library follows an Atomic Design vocabulary, but uses it as an engineering map rather than a taxonomy for its own sake:

| Layer | What it contains | Why it matters |
| --- | --- | --- |
| Sub-atoms | Tokens, accessibility modes, motion and typography rules | Establishes the visual language |
| Atoms | Button, Icon, Toggle, Pill, Tab, Loader | Makes primitive behavior reusable |
| Molecules | Summary, Tooltip, Navigation Menu, Video Controls | Encodes recurring interaction patterns |
| Organisms | Header, Article, Gallery, Video Player | Solves complete interface responsibilities |
| Templates | Case View, Home View, Player View | Composes product-level experiences |

This separation makes a change easier to reason about. A spacing adjustment belongs to a token; a keyboard interaction belongs to the component that owns it; a reading-flow decision belongs to the consuming template.

## Storybook as a development surface

Storybook is more than a catalog here. It is the place where a component’s API, edge cases, visual states, and accessibility behavior become inspectable. The Canvas gives immediate feedback; the Docs tab explains the contract; controls let a developer test real prop combinations without first wiring a full application.

```js
export const Reflow = {
  args: {
    label: 'reflow',
    count: 3,
    background: '#7ED321'
  }
};
```

That workflow changes the feedback loop. Instead of asking whether a component works only inside a page, the team can ask better questions earlier: Does a long label reflow? Is the focus state visible? What happens when the count changes? Can the same API express loading and disabled states?

[INSERIR IMAGEM 3 — Storybook Controls: mostre um componente no Canvas com o painel Controls aberto, incluindo label, cor e slider de quantidade. O print deve evidenciar que a API é explorável por pessoas técnicas e não técnicas.]

## Accessibility is a global capability

Valence treats accessibility as a system-level concern. The consuming application can toggle modes from the document root and let the component library respond consistently:

```html
<html class="a11y-dark-mode a11y-focus-mode">
  <body>
    <ds-header></ds-header>
  </body>
</html>
```

The available modes include dark theme, high contrast, large text, reduced motion, dyslexia-friendly typography, visible focus, forced colors, live-region highlighting, and vision-deficiency simulations. In Storybook, these modes are exposed as global controls, so accessibility can be evaluated as part of normal component development instead of as a final audit.

This is especially important for Portfoliable. The portfolio runtime can own user preference and state, while Valence owns the consistent visual response across headers, articles, players, navigation, and controls.

## Integration without losing boundaries

Portfoliable consumes Valence through ordinary Web Platform contracts. Simple state travels through attributes; rich content enters through slots; user actions return as namespaced custom events:

```html
<ds-case-view
  title-text="Designing a clearer onboarding flow"
  show-language-menu="true">
  <article slot="content">
    <h2>Outcome</h2>
    <p>The case narrative remains owned by the application.</p>
  </article>
</ds-case-view>
```

This keeps ownership clear. Valence provides the interaction surface and visual language; Portfoliable provides the case data, routing, localization, and product context.

## What changed because of Valence

The value of the system is not that every screen looks identical. It is that similarity becomes intentional and difference becomes easier to evaluate. A new component starts with tokens, semantics, documentation, and states instead of a blank stylesheet. A product surface can move faster because its foundational decisions are already shared.

The trade-off is deliberate: native components and explicit contracts require discipline. Consumers must learn the attributes, slots, and events; the system must document APIs instead of hiding behavior in framework magic. In return, the design system stays portable, inspectable, and useful beyond one application.

### The result

- **A reusable foundation:** components can be consumed by Portfoliable and other web applications.
- **A shorter feedback loop:** Canvas, Docs, and Controls make behavior visible early.
- **Accessibility by construction:** modes and interaction states are tested as part of the system.
- **A clearer collaboration model:** design decisions become tokens, APIs, and documented patterns.

Valence is the layer that lets Portfoliable feel coherent without making every case page feel the same. It turns interface craft into shared infrastructure—and keeps that infrastructure close to the open web.

Explore the [Valence repository](https://github.com/portfoliablejs/valence) or see how it supports the [Portfoliable runtime](https://github.com/portfoliablejs/portfoliable).

# Valence: transformando decisões de interface em sistema

O Valence é o design system de Web Components que sustenta o Portfoliable. Ele nasceu para resolver um problema comum em produtos com interfaces em crescimento: depois que os primeiros componentes são criados, a consistência vira um problema de coordenação. As cores se afastam, padrões de interação são copiados, correções de acessibilidade chegam tarde e cada nova tela reabre as mesmas decisões.

A resposta não foi criar um catálogo maior de componentes. Foi estabelecer uma base mais clara: Web Standards, um conjunto pequeno de tokens de design, composição previsível e um espaço em que cada componente pode ser explorado antes de chegar à produção.

> Um design system não é apenas uma coleção de componentes. É uma forma compartilhada de tomar decisões.

[INSERIR IMAGEM 1 — Hero do Valence: um print amplo do Storybook com a navegação lateral, uma área de Canvas e um componente central em destaque. O enquadramento deve fazer o sistema parecer um produto de desenvolvimento, não apenas uma galeria.]

## Construído sobre a plataforma web

O Valence usa custom elements nativos em vez de prender o sistema a um único framework. Um componente pode ser consumido pelo Portfoliable hoje e continuar disponível para outra aplicação JavaScript amanhã:

```js
import '@portfoliablejs/valence';

const button = document.createElement('ds-button');
button.setAttribute('label', 'Abrir case');
button.setAttribute('variant', 'primary');
document.querySelector('#actions').append(button);
```

Os componentes encapsulam comportamento e estilos por meio de Shadow DOM. Isso cria uma fronteira forte: os estilos da aplicação não reescrevem acidentalmente um botão, e um componente pode evoluir sem obrigar cada consumidor a copiar seu CSS. Também mantém o design system próximo do modelo nativo do navegador — atributos, slots, eventos e HTML semântico.

## Uma estrutura que acompanha a interface

A biblioteca segue um vocabulário de Atomic Design, mas o utiliza como mapa de engenharia, e não como uma taxonomia por si só:

| Camada | O que contém | Por que importa |
| --- | --- | --- |
| Sub-atoms | Tokens, modos de acessibilidade, movimento e tipografia | Estabelece a linguagem visual |
| Atoms | Button, Icon, Toggle, Pill, Tab, Loader | Reutiliza comportamentos primitivos |
| Molecules | Summary, Tooltip, Navigation Menu, Video Controls | Codifica padrões recorrentes |
| Organisms | Header, Article, Gallery, Video Player | Resolve responsabilidades completas |
| Templates | Case View, Home View, Player View | Compõe experiências de produto |

Essa separação torna as mudanças mais fáceis de raciocinar. Um ajuste de espaçamento pertence a um token; uma interação de teclado pertence ao componente que a possui; uma decisão de fluxo de leitura pertence ao template consumidor.

## Storybook como superfície de desenvolvimento

O Storybook é mais do que um catálogo. É o lugar onde API, casos extremos, estados visuais e comportamento acessível se tornam inspecionáveis. O Canvas dá feedback imediato; a aba Docs explica o contrato; os controles permitem testar combinações reais de props sem primeiro conectar uma aplicação inteira.

```js
export const Reflow = {
  args: {
    label: 'reflow',
    count: 3,
    background: '#7ED321'
  }
};
```

Esse fluxo muda o ciclo de feedback. Em vez de perguntar se um componente funciona apenas dentro de uma página, a equipe pode fazer perguntas melhores mais cedo: um label longo se reorganiza? O estado de foco está visível? O que acontece quando a quantidade muda? A mesma API representa os estados de carregamento e desabilitado?

[INSERIR IMAGEM 3 — Storybook Controls: mostre um componente no Canvas com o painel Controls aberto, incluindo label, cor e slider de quantidade. O print deve evidenciar que a API é explorável por pessoas técnicas e não técnicas.]

## Acessibilidade como capacidade global

O Valence trata acessibilidade como uma preocupação do sistema. A aplicação consumidora pode alternar modos a partir da raiz do documento e deixar que a biblioteca responda de forma consistente:

```html
<html class="a11y-dark-mode a11y-focus-mode">
  <body>
    <ds-header></ds-header>
  </body>
</html>
```

Os modos incluem tema escuro, alto contraste, texto grande, redução de movimento, tipografia amigável para dislexia, foco visível, forced colors, destaque de live regions e simulações de deficiências visuais. No Storybook, esses modos aparecem como controles globais, permitindo avaliar acessibilidade como parte do desenvolvimento normal, e não apenas como auditoria final.

Isso é especialmente importante para o Portfoliable. O runtime pode cuidar da preferência e do estado da pessoa usuária, enquanto o Valence cuida da resposta visual consistente entre headers, artigos, players, navegação e controles.

## Integração sem perder fronteiras

O Portfoliable consome o Valence por meio de contratos comuns da Web Platform. Estados simples viajam por atributos; conteúdo rico entra por slots; ações da pessoa usuária retornam como eventos customizados com namespace:

```html
<ds-case-view
  title-text="Criando um onboarding mais claro"
  show-language-menu="true">
  <article slot="content">
    <h2>Resultado</h2>
    <p>A narrativa do case continua pertencendo à aplicação.</p>
  </article>
</ds-case-view>
```

Essa divisão mantém as responsabilidades claras. O Valence fornece a superfície de interação e a linguagem visual; o Portfoliable fornece dados dos cases, rotas, localização e contexto do produto.

## O que mudou por causa do Valence

O valor do sistema não está em fazer toda tela parecer igual. Está em tornar a semelhança intencional e a diferença mais fácil de avaliar. Um novo componente começa com tokens, semântica, documentação e estados, em vez de começar com uma stylesheet vazia. Uma superfície de produto pode avançar mais rápido porque suas decisões fundamentais já são compartilhadas.

A troca também é deliberada: componentes nativos e contratos explícitos exigem disciplina. Consumidores precisam conhecer atributos, slots e eventos; o sistema precisa documentar APIs em vez de esconder comportamento em abstrações de framework. Em troca, o design system permanece portátil, inspecionável e útil além de uma única aplicação.

### O resultado

- **Uma base reutilizável:** componentes podem ser consumidos pelo Portfoliable e por outras aplicações web.
- **Um feedback mais curto:** Canvas, Docs e Controls tornam o comportamento visível cedo.
- **Acessibilidade desde a construção:** modos e estados de interação são testados como parte do sistema.
- **Uma colaboração mais clara:** decisões de design viram tokens, APIs e padrões documentados.

O Valence é a camada que permite ao Portfoliable ser coerente sem fazer cada case parecer igual. Ele transforma o cuidado com a interface em infraestrutura compartilhada — mantendo essa infraestrutura próxima da web aberta.

Conheça o [repositório do Valence](https://github.com/portfoliablejs/valence) ou veja como ele sustenta o [runtime do Portfoliable](https://github.com/portfoliablejs/portfoliable).
